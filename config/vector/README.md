# NanoSIEM Vector Configuration

This directory contains the Vector configuration for NanoSIEM's log ingestion pipeline.

## Directory Structure

```
config/vector/
├── 00-base.toml              # Core pipeline: sources, auth, rate limiting
├── 20-dynamic-router.toml    # Auto-generated router (DO NOT EDIT)
├── 50-generic-parser.toml    # Generic parser for unknown source types
├── 90-sinks.toml             # Output sinks (NanoSIEM API, Prometheus)
├── sinks/
│   ├── clickhouse.toml.disabled  # Direct ClickHouse sink (optional)
│   └── *.bak                     # Backup sink configurations
├── sources/
│   └── parsers/              # Deployed parser configs (auto-generated)
│       ├── _combiner.toml    # Combines all parser outputs
│       └── *.toml            # Individual parser configs
├── certs/                    # TLS certificates (optional)
└── *.bak                     # Backup files (not loaded)
```

## File Loading Order

Vector loads `.toml` files alphabetically. The naming convention ensures proper ordering:

1. `00-base.toml` - HTTP source, auth, rate limiting, content parsing
2. `20-dynamic-router.toml` - Routes logs to parsers based on source type
3. `sources/parsers/*.toml` - Individual parser transforms
4. `50-generic-parser.toml` - Handles unknown source types
5. `90-sinks.toml` - Sends logs to NanoSIEM API

## Dynamic Router

The `20-dynamic-router.toml` file is **automatically generated** when parsers are deployed via the UI. It contains:

- Routes for each deployed parser (e.g., `apache`, `nginx`)
- Routes for built-in source types (e.g., `windows_event`, `syslog`)
- Placeholder transforms for source types without deployed parsers
- A catch-all `generic` route for unknown source types

**DO NOT EDIT THIS FILE MANUALLY** - changes will be overwritten on next parser deployment.

## Adding a New Parser

1. Create the parser in the NanoSIEM UI (Parsers → New Parser)
2. Set source type to "routed" for HTTP-ingested logs
3. Write VRL code to parse and extract UDM fields
4. Click "Deploy" to generate the config and reload Vector

The deployment process:
1. Validates VRL syntax
2. Generates parser config file in `sources/parsers/`
3. Updates `20-dynamic-router.toml` with new route
4. Updates `_combiner.toml` to include parser output
5. Signals Vector to reload config (sub-second, no data loss)

## Source Type Routing

Logs are routed based on the `X-Source-Type` header or `source_type` field in the body:

```bash
# Send Apache logs
curl -X POST http://localhost:8080/ \
  -H "Authorization: Bearer your-token" \
  -H "X-Source-Type: apache" \
  -H "Content-Type: text/plain" \
  -d '192.168.1.1 - - [21/Dec/2025:10:30:45 +0000] "GET /api HTTP/1.1" 200 1234'

# Send custom app logs
curl -X POST http://localhost:8080/ \
  -H "Authorization: Bearer your-token" \
  -H "X-Source-Type: my_custom_app" \
  -H "Content-Type: application/json" \
  -d '{"message": "User logged in", "user": "john"}'
```

## Environment Variables

- `VECTOR_AUTH_TOKEN` - Bearer token for authentication (default: `nanosiem-default-token`)
- `NANOSIEM_INGESTION_URL` - API endpoint for log delivery (default: `http://host.docker.internal:3000/api/ingest`)
- `VECTOR_DATA_DIR` - Directory for disk buffer persistence

### ClickHouse Direct Sink Variables (optional)

When using the direct ClickHouse sink (`sinks/clickhouse.toml`):

- `CLICKHOUSE_URL` - ClickHouse HTTP interface URL (default: `http://clickhouse:8123`)
- `CLICKHOUSE_DATABASE` - Database name (default: `nanosiem`)
- `CLICKHOUSE_USER` - Username (default: `nanosiem`)
- `CLICKHOUSE_PASSWORD` - Password (default: `nanosiem`)

## Vector Reload

When parsers are deployed, Vector reloads its configuration:

- **Hot reload** - No process restart, sub-second config swap
- **No data loss** - Incoming data is buffered during reload
- **Automatic** - Triggered via Vector API on port 8686

## Backup Files

Files ending in `.bak` or `.disabled` are not loaded by Vector. These contain:
- Previous monolithic configs (`vector-minimal.toml.bak`)
- Alternative sink configurations (`sinks/*.bak`, `sinks/*.disabled`)
- Disabled source configurations (`sources/*.disabled`)

## Sink Options

NanoSIEM supports two ingestion paths:

### 1. NanoSIEM API Sink (Default)

The default configuration in `90-sinks.toml` sends logs through the NanoSIEM API:

```
Vector → NanoSIEM API → ClickHouse
```

**Advantages:**
- API validation and error handling
- Automatic enrichment (GeoIP, ASN)
- Error logging to PostgreSQL
- Consistent with UI uploads

**Best for:** Most deployments, <10k events/sec

### 2. Direct ClickHouse Sink (High Volume)

For high-volume scenarios, Vector can write directly to ClickHouse:

```
Vector → ClickHouse (direct with _inserted_at timestamp)
```

This enables the two-tier detection architecture:
- **Real-Time (10-30s):** ClickHouse materialized views for atomic IOC detections
- **Scheduled (continuous or custom):** Scheduler with 15-second checks for all other detection types

The scheduler checks every 15 seconds and fires rules based on their cron schedule.
Use `*/1 * * * *` for continuous (1-minute) detection.

**To enable:**
1. The configuration files are already in place:
   - `sinks/clickhouse.toml` - ClickHouse sink configuration
   - `transforms/clickhouse_mapping.toml` - Schema mapping transform
   - `transforms/error_handling.toml` - Dead letter queue for failed logs
2. Set ClickHouse environment variables in `.env`:
   ```bash
   CLICKHOUSE_URL=http://clickhouse:8123
   CLICKHOUSE_DATABASE=nanosiem
   CLICKHOUSE_USER=nanosiem
   CLICKHOUSE_PASSWORD=nanosiem
   ```
3. Apply the direct ingestion schema:
   ```bash
   ./scripts/apply-direct-ingestion-schema.sh
   ```
4. (Optional) Disable the API sink in `90-sinks.toml` to use only direct ingestion
5. Restart Vector: `docker-compose restart vector`

**Advantages:**
- Higher throughput (~10k events/sec vs ~1k events/sec)
- Lower latency (direct write vs API hop)
- Enables two-tier detection architecture
- Automatic insertion tracking via `_inserted_at` timestamp

**Trade-offs:**
- Bypasses API validation (validation happens in ClickHouse)
- Enrichment happens post-ingestion (via enrichment service)
- Requires ClickHouse schema knowledge

**Best for:** High-volume deployments, real-time detection requirements

**See:** `sinks/README.md` for detailed setup and troubleshooting

### Parallel Operation (Migration Strategy)

During migration, you can run both sinks in parallel:
- Keep `nanosiem_api` sink enabled in `90-sinks.toml`
- Enable direct ClickHouse sink in `sinks/clickhouse.toml`
- Both sinks receive the same logs
- Compare data to validate consistency
- Once validated, disable the API sink

### Switching Between Sinks

To switch from API to direct ClickHouse:

```bash
# Configuration files are already in place, just set environment variables
# in .env and restart Vector
docker-compose restart vector

# Optionally disable API sink by commenting out [sinks.nanosiem_api] in 90-sinks.toml
```

To switch back to API sink:

```bash
# Comment out the ClickHouse sink in sinks/clickhouse.toml
# Or remove the CLICKHOUSE_* environment variables
# Re-enable API sink in 90-sinks.toml if disabled

# Restart Vector
docker-compose restart vector
```

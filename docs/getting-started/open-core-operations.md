# Open-core operations runbook

> **Scope:** this runbook was written for the gen1 lake profile
> (`COMPOSE_PROFILES=lake`). New installs get the lean profile
> (`COMPOSE_PROFILES=lean`); see
> [open-lean-install.md](../deployment/open-lean-install.md) for it. A
> ClickHouse install cannot be upgraded in place: the installer refuses and
> prints the fresh-install steps.

Clean install, validation, upgrade, rollback and recovery for a nano open-core
deployment — `install.sh` / `get.nano.rs` with `docker-compose.opensource.yml`.

Everything here is verified against the shipped compose files. Commands assume
you are in the install directory (`~/nano` by default) and that
`docker compose version` reports v2 or newer.

---

## 0. What you are running

One storage profile, recorded in `.env` as `COMPOSE_PROFILES=lake`: OCSF 1.9
Iceberg tables on RustFS, queried by the chDB worker
(`NANO_ENABLE_LAKE_CONTROL_PLANE=1`, `NANO_SCHEMA_PROFILE=ocsf`).

> The legacy ClickHouse edition (UDM + the ClickHouse `legacy` compose profile)
> is no longer supported. Its last state lives on the git branch
> `legacy/clickhouse`, unmaintained.

The lake profile runs PostgreSQL, Dragonfly, Vector, nginx and the nano
api/jobs/search/web services alongside the lake services. **PostgreSQL 18 is the only supported major**; the
compose pins it by digest and refuses to start on a data directory written by a
different major (see §4).

The lake profile supports an **8 GiB VM**, allowing up to 512 MiB of kernel
reserve (at least 7,680 MiB visible to Docker). `install.sh` and the initializer
share one startup policy and fit the service and cell budgets within 95% of
actual host memory. See [startup memory sizing](../deployment/open-core-startup-memory.md).

## 1. Clean install

```bash
curl -fsSL https://get.nano.rs | bash
```

Non-interactive:

```bash
NANO_ADMIN_EMAIL=you@example.com \
NANO_ADMIN_NAME="You" \
NANO_ADMIN_PASSWORD='a-password-of-at-least-12-chars' \
NANO_BASE_URL=https://siem.example.com \
  bash install.sh
```

What it does, in order: prerequisites → clone/update → collect admin details →
write `.env` (mode 600, every secret from `openssl rand -hex 32`) →
**PostgreSQL major preflight** → `docker compose pull` → **image digest
verification against `images.lock`** → `up -d` → wait for `/api/health` →
`POST /api/setup/initialize`.

It prints the login URL, the ingest token, and every ingest endpoint. If the
admin password was autogenerated it is also written to `.env` as
`INITIAL_ADMIN_PASSWORD` *before* the image pull, so a mid-install failure
cannot lose it.

### Verify the install

```bash
scripts/smoke-open-core.sh
```

This is the check `install.sh` does not do. It is read-only — it starts,
stops and reconfigures nothing — and it covers:

* **restart loops** — any container currently restarting, or above 3 restarts,
  with the recurring log line;
* one-shot bootstrap services (`postgres-migrate`, `lake-*-init`,
  `lake-catalog-bootstrap`, `lake-worker-config-bootstrap`, the profile guards)
  exited `0`;
* every long-running service is `running`, and `healthy` where it has a
  healthcheck;
* the PostgreSQL data directory matches the pinned major;
* `GET /api/health` returns `ok` and `/api/setup/status` reports initialized;
* the lake query worker's own `/health`, and which generation it is serving.

Run it after every install, upgrade and restart.

> **Why this matters.** Fourteen long-running services in the lake profile carry
> `restart: unless-stopped` and **no healthcheck**, so a failure in the
> publish / compaction / retention lane restarts forever without changing
> `/api/health` — which covers PostgreSQL and the query worker, not those. A
> real validation stack was found with four services at over 3,100 restarts
> each, accumulated silently across two days. `docker ps` said "Restarting";
> nothing else did.

## 2. Routine upgrade (same PostgreSQL major)

Re-run the installer from the install directory. A re-run is the upgrade:

```bash
cd ~/nano
curl -fsSL https://get.nano.rs | bash        # or ./install.sh from the checkout
scripts/smoke-open-core.sh
```

The installer moves the checkout to the newest release, takes the image release
from that checkout's `images.lock`, rewrites `NANO_VERSION` in `.env` to match
(it prints `Image release: <old> → <new>`), pulls, verifies every image digest
against the lock, backfills any newly required secret, re-runs the lean
initializer, and recreates the services. The release recorded in `.env` by an
earlier run is not reused; compose reads `NANO_VERSION` from `.env`, so a
`git pull` + `docker compose pull` + `up -d` by hand would stay on the old
images, and it skips digest verification. Use the installer.

To pin or roll back to a specific release, name it for that run:

```bash
curl -fsSL https://get.nano.rs | NANO_VERSION=1.0.7 bash
```

The installer verifies a pinned release against that release's own
`images.lock`, fetched from the repo with `curl` and `python3` (no Node needed).
If it cannot find that lock, it refuses to start rather than run unverified
images. The pin lasts for that run: the next re-run without `NANO_VERSION`
upgrades to the checkout's release again.

Migrations need no operator action: the one-shot `postgres-migrate` runs to
completion before api/jobs/search start.

## 3. Backups

PostgreSQL holds everything that cannot be re-ingested: users, rules, alerts,
cases, dashboards, audit.

```bash
docker compose -f docker-compose.opensource.yml exec -T postgres \
  pg_dumpall -U "${POSTGRES_USER:-nanosiem}" | gzip > nano-pg-$(date +%F).sql.gz
```

Also keep a copy of `.env` — it holds the encryption key and every service
credential. Without it a restored database is unreadable.

Event data lives in the `nano-lake-object-data` volume; back it up with your
normal volume tooling if re-ingesting is not an option.

## 3a. Network exposure & firewall

> **Use `docker-compose.opensource.yml` for any non-loopback deployment.** The
> repo's `docker-compose.yml` is for **local development only** — it binds
> Postgres, Prometheus (with `--web.enable-admin-api`), Grafana (default
> credentials) and the exporters to `0.0.0.0`. On a host with a public IP those
> become reachable, unauthenticated, from the internet. Never run the dev compose
> on a public host.

`docker-compose.opensource.yml` publishes these host ports:

| Port | Service | Auth | Notes |
|------|---------|------|-------|
| `80` (`443` via TLS overlay) | nginx | JWT at `/api` | The single UI/API entrypoint |
| `8080` | Vector HTTP ingest | `VECTOR_AUTH_TOKEN` (Bearer) | Blank token fails closed |
| `8088` | Vector HEC | `VECTOR_AUTH_TOKEN` | |
| `6000` | Vector native | **none** (trusts forwarder) | `127.0.0.1` unless `NANO_VECTOR_NATIVE_BIND_ADDRESS` is set |
| `4317` / `4318` | OpenTelemetry (raw) | Internal only | Not published; remote OTLP/HTTP uses nginx `/otlp` with an active source-bound credential |
| `24224` | Fluent Forward | — no source by default | `127.0.0.1` unless `NANO_FLUENT_BIND_ADDRESS` is set |

The lake object store, catalog and query worker bind to `127.0.0.1` only.
Postgres, Dragonfly and the api / search / jobs services have **no published
ports** — they live on the internal Docker network. Check the compose `ports:`
lists for anything else your version publishes.

The unauthenticated ports (`6000`, raw `4317/4318`, `24224`) bind to loopback
by default. They are **ingest-only**: a caller can push logs but cannot read
stored data or control the system. Exposing one on a public IP opens a write
surface (log injection, DoS, storage cost), so set its `NANO_*_BIND_ADDRESS`
only on a trusted network, and firewall it there too.

Recommended firewall rules — allow the UI/API, and only the ingest ports you
actually use, scoped to your log sources. Example with `ufw`:

```bash
# Public UI/API (put TLS in front with docker-compose.tls.yml)
ufw allow 80/tcp
ufw allow 443/tcp

# Ingest — restrict to your log-source networks, don't open to the world
ufw allow from 10.0.0.0/8 to any port 8080 proto tcp   # HTTP ingest (token-gated)
ufw allow from 10.0.0.0/8 to any port 6000 proto tcp   # Vector native (only if you use it)

# Everything else stays closed
ufw default deny incoming
ufw enable
```

If a cloud provider security group / network ACL sits in front, mirror the same
rules there and treat the host firewall as defence-in-depth. Do **not** publish
ingest protocols you aren't using — comment them out of the compose `ports:`
list.

## 4. PostgreSQL major-version upgrade

A PostgreSQL server refuses to open a data directory written by a different
major:

```
FATAL:  database files are incompatible with server
DETAIL: The data directory was initialized by PostgreSQL version 17,
        which is not compatible with this version 18.6
```

Because `postgres` is `restart: unless-stopped`, that would otherwise be an
invisible crash loop with every other service stuck waiting on it. Two guards
prevent that:

* `postgres-version-guard` — a one-shot in both compose files that reads
  `PG_VERSION` off the data volume (read-only) and compares it with the pinned
  image's own `PG_MAJOR`. `postgres` gates on it, so a mismatch stops the start
  with the migration command instead of looping.
* `install.sh` runs the same check (`scripts/preflight-postgres-major.sh`)
  *before* the image pull, so an upgrader is not made to wait for it.

### The migration

```bash
cd ~/nano
docker compose -f docker-compose.opensource.yml down     # NOT -v
scripts/upgrade-postgres-major.sh --dry-run              # shows the plan
scripts/upgrade-postgres-major.sh                        # prompts, then runs
docker compose -f docker-compose.opensource.yml up -d
scripts/smoke-open-core.sh
```

The script is non-destructive by construction:

1. byte-copies the existing volume to `<volume>__pg<old>__<timestamp>` — kept
   forever, this is the rollback artifact;
2. runs the **old** server against that copy and `pg_dumpall`s it to
   `./backups/` — a second, independent recovery path;
3. initializes the new major in a scratch volume and restores the dump;
4. **verifies** the restore against the source — database list, per-database
   table counts, the `_sqlx_migrations` row count, and the bootstrap superuser —
   and aborts leaving the original untouched if any of them differ;
5. only then swaps the verified cluster into the volume the compose expects.

Your existing `POSTGRES_PASSWORD` keeps working: `pg_dumpall` carries the role's
SCRAM verifier, so `.env` needs no change.

Re-running it on an already-current volume prints `already on PostgreSQL <n> —
nothing to do` and exits 0.

### Roll back a PostgreSQL upgrade

With the stack stopped, copy the snapshot volume back and re-pin the old major
in the compose (`image:` and the matching `images.lock` line):

```bash
docker run --rm -v <volume>__pg17__<timestamp>:/from:ro -v <volume>:/to \
  postgres:18@sha256:... sh -c 'find /to -mindepth 1 -delete; cd /from && cp -a . /to/'
```

Or restore the SQL dump into a fresh cluster of the old major. Both paths were
rehearsed end to end.

## 5. Recovery

### The stack is up but a service is crash-looping

```bash
scripts/smoke-open-core.sh          # names the container, count, and last error
docker logs --tail 100 <container>
```

Signatures seen in practice on the lake profile:

| Log line | Meaning |
|---|---|
| `TableNotFound => Tried to load a table that does not exist` (retention-manager / tail-compactor / event-publisher) | The Iceberg event table is missing — the catalog was reset, or `lake-catalog-bootstrap` never completed. Check `docker logs nano-lake-catalog-bootstrap`. |
| `failed to read native chDB artifact: No such file or directory` (query-worker) | `worker.json` pins a chDB artifact that is not in the `nano-lake-runtime` volume — usually a partial image rollout. Confirm every lake image is on the same release, then re-run `scripts/rollout-lake-runtime.sh`. |
| `Container ... is restarting, wait until the container is running` from a tool | Not transient; that container is looping. Check its restart count. |

Restarting a looping service without fixing the cause just resets the counter —
which is the signal `smoke-open-core.sh` reads.

### `install.sh` fails at `docker compose pull` with 403/401

That GHCR package is not public. The error names the repository. Either
`docker login ghcr.io` with an account that has access, or wait for the package
to be published. **Known:** `nano-lake-control`, `nano-lake-maintenance` and
`nano-lake-query` are not anonymously pullable today, which blocks fresh
installs on the default (lake) profile. `nano-api`, `nano-search`, `nano-jobs`
and `nano-web` are public.

### `install.sh` refuses with an images.lock coverage error

An image the compose deploys has no `images.lock` entry, so its digest cannot be
verified. Regenerate the lock (CI's `merge-manifests` writes one line per built
component) — or, if you accept unverified images, re-run with
`NANO_SKIP_IMAGE_VERIFY=1`.

### API never becomes healthy

```bash
docker compose -f docker-compose.opensource.yml ps
docker compose -f docker-compose.opensource.yml logs postgres-version-guard    # PG major mismatch stops here
docker compose -f docker-compose.opensource.yml logs postgres-migrate          # PostgreSQL schema
docker compose -f docker-compose.opensource.yml logs nano-api
```

On the lake profile also check `nano-lake-profile-guard`: it fails closed on a
mixed `COMPOSE_PROFILES`, a `NANO_LOG_QUERY_BACKEND` that is not `lake`, any of
20 required secrets left empty or `CHANGE_ME`, and a `NANO_LAKE_WORKER_SOURCE`
that does not match `NANO_LAKE_EVENT_TABLE_LOCATION_PREFIX`.

### Full reset (destroys all data)

```bash
docker compose -f docker-compose.opensource.yml down -v
```

`-v` removes every volume, including PostgreSQL. Take a `pg_dumpall` first.

```bash
scripts/check-opensource-pins.sh            # stack definition: pins, profiles, vector config, PG guard
scripts/check-build-context-includes.sh     # every compile-time asset survives .dockerignore
scripts/test-install-image-verification.sh  # install.sh's supply-chain check
```

All three are fast, need no running stack (the first two need a Docker daemon),
and run in CI as `opensource-stack-gate`.

## 7. Running the lake locally against host services

For development, the lake control plane runs in Compose while api/search/jobs
run from source on the host:

```bash
COMPOSE_PROFILES=lake docker compose -f docker-compose.opensource.yml up -d
./scripts/start-microservices-dev.sh --lake
```

`--lake` discovers the running query worker, copies its `worker.json` and OCSF
source manifest out of the `nano-lake-runtime` volume (cross-checking the
generation against the worker's `/health` so a promotion racing the start is
caught), and derives the tenant, Bronze bucket and RustFS credentials from them.
Add `--check` to print the resolved configuration and exit without starting
anything.
